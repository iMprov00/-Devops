# Разбор инцидента ops-statusboard

> Шпаргалка №9 по учебной практике от 25.11.2026. Это **практика с подсказками**, не самостоятельный экзамен и не сдача всего раздела Linux. Источник — отчёт наставника, не оригинальные логи. Полный путь к файлу, имя unit и тела ответов здесь не приводятся.

## Что увидели

Процесс на Python работал на порту **8088**, unit был **active** (активен: процесс службы запущен). По HTTP пришёл код **503** и текст `status file not found`. Код 503 значит: приложение **уже ответило** ошибкой. Это не проблема TCP: соединение установилось, ошибку вернуло уже приложение, а не «подключиться не удалось».

В ответе **/health** было `false`. Поле в теле ответа и код HTTP — разные факты: они **не всегда** согласованы.

Максим смотрел `systemctl status`, журнал (`journalctl`), `curl`, дерево каталогов (`tree`), лог и `systemctl cat`. По определению unit: `User=improv`, переменная `STATUSBOARD_FILE` указывала на `.../data/status.json` (полный путь в отчёте не зафиксирован). Каталог `data` был пуст. Файл `archive/status-current.json` существовал, владелец и группа — `root:root`, режим — `600`.

`systemctl cat` показывает определение unit и подключения (drop-in), а не обязательно тот же эффективный набор переменных уже запущенного процесса, если определение меняли и не применяли заново.

## Главный вывод

**Работающий процесс не означает, что приложение может выполнить запрос.** `active` подтверждает, что процесс жив, но не то, что он находит нужный файл и отвечает успешно.

Сначала сверь **ожидаемый путь** (переменная в определении unit) с **реальным файлом** на диске. Затем проверь, может ли **служебный пользователь** (`User=`, здесь `improv`) этот файл прочитать.

## Две отдельные проверки: путь и доступ

Их нельзя смешивать.

1. **Путь.** Исходный симптом приложения — «файл статуса не найден». Ожидаемого `data/status.json` не было: каталог `data` пуст. Это **не** доказательство «отказано в доступе» (Permission denied). Исходный симптом — отсутствие файла, его не нужно подменять ошибкой прав.
2. **Доступ к другому файлу.** В архиве файл был, но с `root:root` и режимом `600`. При обычных правах UNIX, без дополнительных ACL (списков доступа), `600` значит: владелец читает и пишет, группа и остальные — нет. Сам факт «владелец root» чтение не запрещает: для всех, кроме владельца, запрещает режим. Пользователь `improv` такой файл прочитать не сможет.

Это две разные находки. Архивный файл не был тем целевым путём, о котором сообщало приложение; исходный симптом — отсутствие целевого файла, а не отказ в чтении архива.

Для файла JSON нужно право **чтения** (`r`), не выполнения (`x`). Чтобы дойти до файла, нужен **проход** (`x`) по **всем родительским каталогам**.

До изменений используй в основном инструменты только для чтения: `ls -l`, просмотр пути, `namei -l` (цепочка владельцев и прав по пути), журнал, `curl`. Процесс, путь, права и HTTP проверяй **по отдельности**. Чтение от имени служебного пользователя можно проверить через `sudo -u` (запуск от другого пользователя), если известны пользователь и путь.

## Что сделано в этой практике (из каталога проекта), не рецепт выполнять снова

По отчёту из каталога проекта выполнили две команды:

```bash
sudo cp archive/status-current.json data/status.json
sudo chown improv:improv data/status.json
```

Так создали отсутствующий целевой файл копией из архива. В этом случае у копии сохранился режим `600`; затем `chown` сменил владельца и группу на `improv`, режим остался `600`. Владелец `improv` теперь может читать и писать этот файл. `chown` применяли только к целевому файлу, без рекурсии (`-R`).

Не считай, что `cp` всегда сохраняет права: без явного сохранения на режим новой копии может повлиять **umask** (маска прав при создании). Здесь по отчёту режим остался `600`.

Копия из архива — **не всегда** корректный и актуальный источник. В этой практике использовали архивную копию. Успешные ответы после восстановления подтверждены; отдельной проверки актуальности содержимого в отчёте нет. В другой ситуации источник нужно проверить до копирования.

Рестарт службы **не делали**. После изменений локально оба адреса — `/status` и `/health` — ответили HTTP 200, в health было `true`; с Windows `/status` дал HTTP 200 и JSON. Это наблюдение говорит, что **данное** приложение подхватило появившийся файл без рестарта. Другое может кэшировать (запоминать) прежнюю ошибку или отсутствие файла — отсутствие рестарта не общая гарантия.

## Как идти дальше

Самостоятельность в этой практике **не подтверждена**: в выборе первого следующего шага были затруднения. Дальше держи порядок: **гипотеза → проверка → минимальное изменение → проверка с двух сторон** (например, локально и с Windows; состояние процесса и HTTP-ответ).

Для самопроверки: почему одновременно возможны `active` и HTTP 503? Чем «файл не найден» отличается от «нет прав на чтение»? Почему одного владельца `root` недостаточно, чтобы сказать «файл нельзя прочитать», и что меняет режим `600`?
