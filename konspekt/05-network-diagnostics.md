## Схема диагностики

Проверяй уровни по отдельности. Успех на одном не доказывает следующий.

1. **IP и маршрут.** У машины есть адрес, и есть путь к цели (своя подсеть или шлюз).
2. **TCP.** Установлено соединение с нужным портом.
3. **HTTP.** Приложение ответило кодом и, при необходимости, телом.

**DNS — отдельно.** Если обращаешься по имени, сначала нужно разрешение имени в адрес, и только потом соединение. Успешный DNS не доказывает, что сайт работает. `ping` проверяет ответ на ICMP, а не работу сайта.

## 1. Адрес, подсеть, маршрут

```bash
ip -br -4 addr
```

`-br` — краткий вывод, `-4` — только IPv4. Пример: `ens18  UP  192.168.50.23/24`. Здесь `ens18` — имя интерфейса, `UP` — «включён». `192.168.50.23` — адрес, `/24` — префикс: первые 24 бита относятся к сети (маска `255.255.255.0`). Учебная сеть — `192.168.50.0`, обычные адреса узлов — от `.1` до `.254`.

```bash
ip route
```

Пример: `default via 192.168.50.1 dev ens18` — «если нет более подходящего маршрута, отправлять через шлюз `192.168.50.1` по интерфейсу `ens18`». **Более специфичные маршруты важнее маршрута по умолчанию (default).**

**Шлюз (gateway)** — соседний маршрутизатор для других сетей. До соседа в своей локальной подсети пакет идёт напрямую: для IPv4 его канальный адрес система узнаёт через ARP. Не всё идёт «всегда через шлюз».

## 2. DNS и NSS

DNS (система доменных имён) помогает получить IP по имени, но не проверяет сайт. На Ubuntu адрес `127.0.0.53` обычно означает локальный посредник (stub) службы `systemd-resolved`, а не внешний DNS провайдера.

```bash
resolvectl status
```

Смотри поля: `Current DNS Server` — текущий выбранный вышестоящий сервер (upstream); `DNS Servers` — список настроенных серверов. Список — не обязательная цепочка: система не обязана опрашивать их всех по порядку.

```bash
getent ahostsv4 example.org
```

`ahostsv4` запрашивает IPv4-адреса. `getent` использует NSS (Name Service Switch — механизм выбора источников имён): `/etc/hosts`, кэш, DNS и другие источники в порядке настроек. Успех не обязан означать новый запрос во внешний DNS. Несколько строк с одним IP и пометками `STREAM`, `DGRAM`, `RAW` — не обязательно разные серверы, это варианты использования адреса.

## 3. Кто слушает порт

```bash
ss -ltnp
```

`-l` — прослушивание (listen), `-t` — TCP, `-n` — адреса и порты числами, `-p` — процесс. Без нужных прав имя процесса может не показаться; это не значит, что слушателя нет.

В столбце `Local Address:Port` (локальный адрес и порт):

- `127.0.0.1:80` — только с этой машины. У Windows и у ВМ **свои** loopback-адреса: `127.0.0.1` в Windows не ведёт в ВМ.
- `0.0.0.0:80` — на всех локальных IPv4-адресах этой машины. Это **не** гарантия доступа из интернета: маршруты и защита остаются отдельными условиями.
- `192.168.50.23:80` — только на этом адресе.
- `[::]` относится к IPv6. Принимает ли такой сокет ещё и IPv4 (dual-stack, двойной стек), зависит от настроек.

## 4. Что доказывают ping, TCP и HTTP

- **ICMP / ping** — машина ответила на служебный сетевой запрос. Ничего не говорит о nginx и сайте.
- **TCP-соединение** — порт принимает соединение. Ещё не доказывает правильную работу сайта.
- **HTTP** — получен ответ приложения.

Если остановить только nginx, ВМ продолжает работать: `ping` может проходить, проверка TCP-порта 80 даёт `False` («ложь», соединение не установлено), а `curl` часто завершается с кодом **7** (не удалось подключиться). Код 7 — это не HTTP 400 и не HTTP 404. После запуска nginx снова проверь именно HTTP, а не только факт запуска службы.

Бывает наоборот: ICMP блокируется, а HTTP работает. **Защиту ради успешного ping не отключай.**

Windows (PowerShell), учебный пример:

```powershell
Test-NetConnection 192.168.50.23 -Port 80
```

`TcpTestSucceeded : True` — «проверка TCP успешна: да», соединение удалось. `PingSucceeded` — отдельный результат ping, не тот же тест.

HTTP-код без тела страницы:

```bash
curl -sS -o /dev/null -w '%{http_code}\n' http://192.168.50.23
```

В PowerShell пиши `curl.exe` и `NUL` вместо `/dev/null`: имя `curl` там может означать другую команду (псевдоним, alias). `-sS` убирает индикатор прогресса, но оставляет сообщения об ошибках.

Код завершения смотри сразу: в Linux — `echo $?`; в PowerShell после `curl.exe` — `$LASTEXITCODE`. Переменная `$?` в PowerShell — логический успех, не числовой код.

**HTTP 404** («не найдено») — сервер ответил, что запрошенного ресурса нет. Это доказывает ответ HTTP-сервера, но **не** исправность всего приложения.

По умолчанию `curl` может вернуть код завершения **0** даже при HTTP 404 или 500: ответ успешно получен, хотя приложение сообщило о проблеме.

**Сообщения об ошибках:**

- `Connection refused` — «в соединении отказано». Часто никто не слушает порт; возможен и явный отказ сетевой защиты. Одну причину по этой фразе не угадывай.
- `Timeout` — «истекло время ожидания». Пакеты могут отбрасываться, узел недоступен, проблема маршрута. Тоже не одна обязательная причина.
- HTTP-код `000` у curl — **не** код ответа сервера: HTTP-ответ не получен.
- Типичные коды curl: **6** — проблема разрешения имени, **7** — проблема подключения, **28** — превышено время ожидания.
